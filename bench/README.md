# bench: CarrierBench and the model-only baseline

Two things live here. `bench/carrierbench/` is the benchmark write-up and runner (Task 27). The files directly under `bench/` are the model-only baseline (Task 22): `sample.py`, `inputs.py`, `baseline.py`, `score.py`, the prompt under `prompts/`, the per-row inputs under `inputs/`, the raw model replies under `outputs/`, and the result in `BASELINE.md` and `BASELINE.json`.

## What CarrierBench is

A synthetic 40-truck Texas carrier over 92 business days, generated by `seed/generate.py` with seed 42: fuel-card transactions, tolls and maintenance invoices with the telematics, tank sizes, contracts, purchase orders, receiving records and vendor bank details needed to check them. Inside it, 52 planted accounts-payable errors in 7 classes and 6 decoys (legitimate unit swaps that look like card misuse until the dispatcher's swap log is read), listed in `seed/fixtures/answer_key.json`. The benchmark question is: given each row and its records, hold or clear, and with which code.

The runner regenerates the fixtures and checks them byte for byte against the commit, reports the counts, computes the controls (held-out trucks and vendors, the decoys, the policy holds) and runs the machine audit: the Python mirror of the kernel (`seed/mirror.py`) must raise every answer-key row from the row's own evidence, so every planted error is inferable from the records and not only from the key.

## Run CarrierBench from a bare clone

Python 3.12 or newer, standard library only. One command:

```sh
git clone <repo> && cd dispatch-ledger
python3 bench/carrierbench/carrierbench.py --seed 42
```

Writes `bench/carrierbench/REPORT.md` and `REPORT.json`. Exit code 0 means the fixtures match the commit and the regeneration, and every answer-key row passed the audit. About 5 seconds on a laptop (the generator takes about 3 of them). `--no-regenerate` skips the generator and only compares the working tree with the commit.

The oracle ceiling and the saboteur run are beside it:

```sh
python3 bench/carrierbench/oracle.py                     # writes bench/carrierbench/oracle.json, under a second
(cd spacetimedb && npm ci) && bash bench/carrierbench/saboteur_run.sh   # writes bench/carrierbench/saboteur.json, under a second after install
```

The oracle is the kernel handed the answer key (every planted row held, every decoy cleared with no question, clean rows posted under the same auto-pay limits), computed from the fixtures with the mirror; it is the end-to-end ceiling the measured run is compared against. The saboteur test feeds a lying finding (recommendation clear, confidence 0.99, fabricated evidence) through the real reducers in the in-process module harness and asserts that `approve_payment` as the agent identity is refused, that no payment row exists, that the hold is still a person's decision, and that the refusal is an audit row. It lives at `spacetimedb/src/saboteur.test.ts` because the module's vitest config includes `src/**/*.test.ts` only, and it imports only vitest and the harness (the module tsconfig has no node types and `spacetime publish` typechecks that folder), so `saboteur_run.sh` carries the observed rows out through vitest's JSON reporter and writes them here.

## Run the model-only baseline from a bare clone

The baseline needs the agent virtual environment (httpx and python-dotenv) and two keys in `.env` at the repo root: `ANTHROPIC_API_KEY` for Claude Sonnet and `ASI_ONE_API_KEY` for asi1-mini. Keys are read from `.env` and never printed.

```sh
python3 -m venv agent/.venv && agent/.venv/bin/pip install -r agent/requirements.txt
agent/.venv/bin/python bench/sample.py && agent/.venv/bin/python bench/inputs.py \
  && agent/.venv/bin/python bench/baseline.py --model sonnet \
  && agent/.venv/bin/python bench/baseline.py --model asi1 \
  && agent/.venv/bin/python bench/score.py
```

What it does: a stratified sample of 558 rows (all 52 planted, all 6 decoys, 500 clean rows; the 6 auto-pay policy holds are left out because they are not exceptions), one input file per row holding exactly the records the kernel sees for it (no answer-key field, no planted marker), one prompt (`bench/prompts/hold_or_clear.txt`), one attempt per row, and a scorer that reads the answer key. Caliber's own figures are read from `docs/FACTS.json`, the measured 92-day run, and are never recomputed by the bench.

Expected runtime and cost, from the committed run (`bench/BASELINE.md`, "Run facts"): Claude Sonnet runs concurrently and finishes in minutes, priced from the response usage at list rates with a hard stop at $15; asi1-mini is paced to the free plan (100 requests per 15 minutes, 1,000 per day), so 558 rows take about 85 minutes. `baseline.py` skips rows that already have an ok output, so a stopped run resumes. `score.py` rewrites `BASELINE.md` and `BASELINE.json` from the raw replies on disk.

## Run the Droid investigator table from a bare clone

Python 3.12 or newer, standard library only, no keys, no network. One command:

```sh
git clone <repo> && cd dispatch-ledger
python3 bench/carrierbench/droid_table.py
```

Reads the 52 recordings in `seed/fixtures/investigations/` (and the originals in `_v1/` of the 7 that were re-recorded), the two cost logs and `droid_listTools_2026-10-24.txt` in `docs/evidence/`, and `worker/src/droid.ts` for the autonomy setting. Writes `bench/carrierbench/droid_table.json` and rewrites the section "Droid investigator, 52 recorded runs" at the end of `docs/RESULTS.md` from it; `--no-results` writes the JSON only. Under a second. The BENCHMARK block (do the controller questions name the planted person or record) is the only part that reads `seed/fixtures/answer_key.json`; the script is the scorer, the agent never sees the key. `scripts/facts.py` rewrites `docs/RESULTS.md` whole, so run this after a full run to put the section back.

## Prompt condition

One prompt was run: the hinted condition. `bench/prompts/hold_or_clear.txt` names the seven codes and their thresholds (25 miles and 30 minutes, tank plus 10 percent, 10 minutes, 30 days, 5 percent, the received quantity, $5,000 within 7 business days) before asking hold or clear. A bare condition, in which the model is given the records and the question with no code list, was not run; the note in `docs/paper/caliber.pdf` says so and reports the hinted condition only.

## Caveat

Synthetic data from the same generator as the clean rows (seed/generate.py, seed 42). Every system was given identical inputs. No fine-tuning, no examples, one prompt, one attempt per row. The result measures whether each system finds what we planted, not how it behaves on a real carrier's statements. A decoy counts as a correct hold for every system: the records on file cannot clear it, only the swap log and a person can.
